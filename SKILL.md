# OneDev Integration

OneDev is a self-hosted, all-in-one DevOps platform: Git hosting, issue tracker, kanban, CI/CD pipelines, and package registry — all in one Java server typically reached on port `6610`. This skill teaches an AI agent how to authenticate to a OneDev server and operate every major surface it exposes.

There are **two ways** to talk to OneDev. Pick based on what the user has running:

| Method | When to use |
| --- | --- |
| **MCP server (`tod mcp`)** | Default for OneDev **13.0 and later**. Highest-level, AI-first interface. ~25 typed tools + 4 guided prompt templates. |
| **REST API** | Works on any OneDev version. Use when MCP isn't available, when scripting in non-AI contexts, or for endpoints MCP doesn't cover (user/group admin, settings, package upload, etc.). |

If unsure which version the user runs, ask once, or attempt MCP first and fall back.

## 1. Authentication — always the first step

Every call against OneDev requires a **personal access token**. The token is generated by the human user from the OneDev web UI:

1. Click the user avatar → **Access Tokens**.
2. Click **New Access Token**, name it (e.g. `ai-agent`), and select permissions.
3. Permissions matter — common scopes the agent will likely need:
   - `Read Code` and `Write Code` (for branches, pushes, PR creation)
   - `Manage Issues` (create/edit/transition issues, add comments)
   - `Run Job` (trigger CI/CD jobs)
   - `Manage Pull Requests` (create/approve/merge PRs)
4. Copy the token value **immediately** — OneDev shows it only once.

Treat the token like a password. Never echo it back to the user in plaintext, never paste it into log files, and never include it in URLs visible to anyone else.

### How the token is sent

For REST: send as HTTP basic auth or as a bearer token:

```http
Authorization: Bearer <token>
```

(Equivalently `-u <username>:<token>` works with `curl`.)

For MCP: store the token in `$HOME/.todconfig`:

```ini
server-url=https://onedev.example.com
access-token=<token>
```

The `tod` binary reads this file automatically — no token needs to flow through prompts.

## 2. Setting up the MCP server (preferred for OneDev 13+)

The MCP server lives inside a small Go binary called **`tod`** ("TheOneDev"), shipped as a separate release. Steps:

1. **Download `tod`** for the user's OS from the OneDev project's build artifacts (`https://code.onedev.io/onedev/tod/~builds`) and place it on `$PATH`. Verify with `tod --help`.
2. **Create `~/.todconfig`** with `server-url` and `access-token` as shown above.
3. **Smoke-test**: run `tod mcp` from a terminal. It should print nothing and block waiting for input — that's success. `Ctrl+C` to exit. If it errors, the token or URL is wrong.
4. **Wire it into the AI client** (Cursor, Claude Desktop, Continue, etc.):

```json
{
  "mcpServers": {
    "OneDev": {
      "command": "tod",
      "args": ["mcp", "--log-file", "/tmp/tod.log"]
    }
  }
}
```

5. **Working directory matters.** Many MCP tools default to the project of the current Git remote. Either run the AI client from a folder that is a clone of a OneDev project, or call `setWorkingDir` explicitly to point at one. `getCurrentRemote` and `getCurrentProject` are the introspection tools to confirm context.

The full list of MCP tools and their parameters is in [`references/mcp-tools.md`](references/mcp-tools.md). Read that file before composing any non-trivial MCP call — argument names and reference formats are easy to misremember.

## 3. Using the REST API directly

When the MCP path isn't available, talk to OneDev's REST API at `https://<host>/~api/...`. Every OneDev install ships interactive API docs at `https://<host>/~help/api` — when in doubt, point the user there or fetch that page to discover endpoint details for their exact version.

Common building blocks:

```bash
# Identity check — always works if the token is valid
curl -H "Authorization: Bearer $TOKEN" https://onedev.example.com/~api/users/me

# List projects you can see
curl -H "Authorization: Bearer $TOKEN" https://onedev.example.com/~api/projects

# Create an issue (POST a JSON body)
curl -X POST -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"projectId": 1, "title": "Something broke", "description": "Details..."}' \
     https://onedev.example.com/~api/issues

# Trigger a CI/CD job via the dedicated endpoint
curl -X POST "https://onedev.example.com/~api/trigger-job?project=my-app&job=ci&branch=main&access-token=$TOKEN"
```

For a fuller catalogue of REST endpoints and payload shapes, see [`references/rest-api.md`](references/rest-api.md).

> Always prefer `https://`. The `trigger-job` endpoint accepts the token as a URL parameter, which means it leaks through proxy logs over HTTP.

## 4. OneDev's query language — the key to power

Issues, pull requests, builds, projects, and commits all share one expressive query language built on ANTLR. Most MCP query tools (`queryIssues`, `queryPullRequests`, `queryBuilds`) accept a `query` string in this language. Mastering it is the difference between "list 50 recent issues" and "high-priority bugs assigned to me that block a release".

Skeleton: `<Field> <operator> <value> [and|or <Field> <operator> <value>] [order by <Field> asc|desc]`

Common operators: `is`, `is not`, `is greater than`, `is less than`, `contains`, `is empty`, `is current` (for "in this project"), `is me` (for "assigned to me").

Examples a user can paste straight in:

| Goal | Query |
| --- | --- |
| Open issues assigned to me | `"State" is "Open" and "Assignees" is me` |
| High-priority bugs not yet in progress | `"Type" is "Bug" and "Priority" is "Major" and "State" is "Open"` |
| Sub-issues of #4 still in progress | `"Parent Issue" is #4 and "State" is "In Progress"` |
| PRs awaiting my review | `"To Be Reviewed By" is me` |
| Builds for the `main` branch that failed today | `"Branch" is "main" and "Status" is "Failed" and "Submit Date" is greater than "1 day ago"` |
| Issues fixed between two release tags | `fixed between build "v1.2.0" and build "v1.3.0"` |
| Combine and order | `"State" is "Open" and "Assignees" is me order by "Priority" desc` |

Quoting rules: field names and string values use **double quotes**; issue/PR/build references use `#NUMBER` unquoted. The full grammar reference (with every supported field per entity type) is in [`references/query-language.md`](references/query-language.md).

## 5. Reference formats — the agent will see these constantly

Most tools accept short references that resolve to a specific entity. Three equivalent forms:

| Form | Example | Means |
| --- | --- | --- |
| `#<number>` | `#42` | Item 42 in the **current** project (working-dir aware) |
| `<project>#<number>` | `my-app#42` | Item 42 in project `my-app` |
| `<key>-<number>` | `MYAPP-42` | Item 42, addressed via the project's short key |

This format is identical for issues, pull requests, and builds — context determines the type.

## 6. Recipes — copy these patterns

The MCP tool names below are the canonical ones from `tod mcp`. For REST-only flows, swap to the equivalent `~api/...` calls.

### 6a. Triage open bugs and create a sub-task

1. `queryIssues` with `"Type" is "Bug" and "State" is "Open" order by "Priority" desc`.
2. Pick the top result; call `getIssue` for full context (description, custom fields, current assignee).
3. `getIssueComments` if there's discussion to read.
4. `createIssue` with a concise title and description; use the `linkIssues` tool with `linkName: "Sub Issues"` to attach it to the parent.
5. Confirm to the user with the new issue reference — do **not** auto-assign or auto-transition unless asked.

### 6b. Ship a fix end-to-end (issue → branch → PR → merge)

1. `changeIssueState` to `In Progress` (this often triggers a state-description workflow that creates/checks out a branch — let it).
2. Make code changes locally; commit and push to the OneDev remote.
3. `createPullRequest` with `sourceBranch`, optional `targetBranch` (defaults to repo default), `title`, `description`, `reviewers`.
4. Optionally `runJob` against the source branch to pre-flight CI.
5. Use the `review-pull-request` prompt template to do a structured review (calls `getPullRequestFileChanges`, `getPullRequestFileContent`, then `processPullRequest` with `approve` / `requestChanges`).
6. `processPullRequest` with `operation: merge` once approvals/CI are green. Linked issues auto-close per the project's workflow.

### 6c. Investigate a red build

1. `getBuild` with the build reference (e.g. `#137`) for status and metadata.
2. `getBuildLog` to read the failure.
3. `getFileChangesSincePreviousSuccessfulSimilarBuild` to see what changed since the last green run — this is the single highest-signal call for triaging regressions.
4. `getBuildSpecSchema` and the file content of `.onedev-buildspec.yml` if the suspect is the pipeline definition itself.
5. Propose a fix; if it's a build-spec change, call the `edit-build-spec` prompt template to apply it correctly against the schema.

### 6d. Run a CI job against uncommitted local changes

This is what `tod run-local` exists for — no need to commit/push to test:

```bash
cd /path/to/clone-of-onedev-project
tod run-local <job-name>                 # basic
tod run-local -p env=staging ci          # with parameters
```

Logs stream live; `Ctrl+C` cancels the remote job.

## 7. The four guided prompt templates

When the MCP server is connected, four "prompts" appear alongside the tools. They are pre-baked workflows the AI can invoke instead of orchestrating tool calls by hand. Prefer them when the user's request matches:

- **`change-issue-state`** — transitions an issue and runs any state-description side effects (e.g. branch creation). Args: `issueReference`, `instruction`.
- **`edit-build-spec`** — fetches the schema, reads the existing `.onedev-buildspec.yml`, applies an instruction, validates, saves. Args: `instruction`.
- **`investigate-build-problems`** — the recipe in §6c, automated. Args: `buildReference`, optional `instruction`.
- **`review-pull-request`** — fetches changes, examines files, decides approve/requestChanges/comment. Args: `pullRequestReference`, `sinceLastReview` (true/false), optional `instruction`.

## 8. Permissions, safety, and good manners

- **Read before write.** When asked to "fix issue #x", call `getIssue` first. Don't blindly transition state without context.
- **Mind the blast radius.** `processPullRequest merge` and `changeIssueState` can trigger automation chains (auto-merges, deploys, notifications). For destructive or irreversible actions, summarise the planned change and get confirmation unless the user clearly pre-authorised it.
- **Confidential issues exist.** OneDev supports confidential issues even in public projects (`confidential: true` parameter). When creating issues that mention security, credentials, or customer PII, set this flag.
- **Don't fabricate references.** If `queryIssues` returns nothing, say so — don't invent issue numbers.
- **Don't paraphrase the token.** If the user pastes a token, use it; don't repeat it back, abbreviate it, or store it anywhere besides the config file you're configuring on their behalf.
- **Honour the working directory.** Many tools silently default to "current project". Before a write operation, call `getCurrentProject` (or include `project` explicitly in the call) so the user knows which repo will be touched.

## 9. Troubleshooting cheat sheet

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `401 Unauthorized` on every call | Bad/expired token, or wrong permissions | Regenerate token; re-check the scopes for the operation |
| `tod mcp` exits with a config error | Missing/malformed `~/.todconfig` | Re-create it; ensure `server-url` has scheme (`https://`) and no trailing slash |
| MCP tools return "no current project" | Working dir is not inside a Git clone of a OneDev project | `cd` into the clone, or call `setWorkingDir`, or pass `project` explicitly |
| `tod run-local` logs cut off / never stream | Nginx in front of OneDev is buffering | Add `proxy_buffering off;` for `location /~api/streaming` |
| Issue creation rejects required fields | Project has custom required fields | Call `getIssue` on any existing issue to see the field shape, then resend |
| `trigger-job` returns 403 | Token lacks `Run Job` permission for that project | Update token permissions |
| MCP server isn't listed in Cursor/Claude Desktop after config change | Client wasn't restarted | Fully quit and relaunch the AI client |

## 10. When to read the reference files

The three files in `references/` go deeper. Read them on demand — don't load all three for every request:

- **`references/mcp-tools.md`** — read whenever composing an MCP call you haven't made before. It lists every tool with its exact parameters.
- **`references/rest-api.md`** — read for REST flows, or when MCP doesn't cover the operation (admin endpoints, packages, settings).
- **`references/query-language.md`** — read whenever building a non-trivial query string for `queryIssues` / `queryPullRequests` / `queryBuilds` / commit search.

That's the skill. Lead with MCP if the server supports it, fall back to REST otherwise, always authenticate with a scoped access token, and use OneDev's query language to keep results sharp.
